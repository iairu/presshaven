STATUS (addressed 2026-10-16) — all changes in the working tree, tested
(196 dashboard, all Lua suites, 77 pool_manager); stacks pick them up on
the next rebuild/restart.

[1] Pre-build 213s too long / template-clone idea.
    The bottleneck is the per-pool "WordPress seed" phase (~60s): a runtime
    pool already clones the production database (fully configured), then
    redundantly re-applies the same WordPress storefront config via wp-cli.
    That is your "clone + only fill in the delta" idea.
    - Added POOL_FAST_CLONE (ids/.env, default OFF, experimental): a runtime
      pool inherits the storefront from the cloned production DB and skips
      the wp-cli reconfig (~50s/pool saved); content is still mirrored by
      the content-sync step. Enable after confirming a built pool serves the
      shop on your host. Pools 1-3 are never affected.
    - For the delayed-windows pre-build, raise POOL_PARALLEL_BUILDS so N
      pools build in one wave instead of two (your host has 20 cores). The
      report now prints both tips when a build was slow.
    I did NOT ship a full volume-clone-from-a-permanent-template rewrite: it
    changes provisioning/Docker/volume handling I can't verify end-to-end
    here, and a bug there breaks pool creation. FAST_CLONE gets most of the
    win safely and reversibly. I can build the dedicated template pool next
    against the running stack if you want to go further.

[2] Pool removal doesn't reassign existing users.
    The behaviour is correct, but the diagram couldn't show it: the forced
    scale-down releases each window's session then removes the pool, and no
    routing read was taken afterwards, so each window's last segment was
    drawn to the end on a pool already gone. The run now, after scale-down,
    sends each affected window back to the shop once and records where it
    lands -- a new "Reassignment after removal" table shows every window
    whose pool was removed being moved to a surviving pool (or a fresh
    session). Idle scale-down never removes a pool a request recently
    reached, so there is normally no active owner to move.

[3] CPU graph should use the sum of all logical processors.
    The run reads the host CPU count; the figure's CPU panel is normalised
    to "% of all N CPUs" (100% = every core busy) instead of "% of one
    CPU". The scale-down table's measured CPU row is normalised the same way.

[4] Memory ~4GB vs ~12GB cap.
    The figure counts the honeypot pool containers only; the host also runs
    production, Redis, Suricata, etc. The memory panel now draws the whole-
    host RAM in use (grey) next to the pool containers (blue), and a new
    "Why pool memory is below the budget" table breaks it down: measured
    per-pool use (~430 MB) vs the budget charge (POOL_RESERVE_MEM_MB) vs the
    1536 MB container limit vs the whole-host total. A WordPress pool idles
    far below both its budget charge and its hard limit, so 10 pools sit
    well under a 12 GB budget; the ~12 GB you saw is the whole host.
